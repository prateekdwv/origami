# India Railway 2026

The current data-collection target is **scheduled passenger services across India
on 15 October 2026, 00:00–24:00 IST**, including suburban/local trains. Collected
snapshots and coverage reports live in [assets/schedules/](assets/schedules/README.md).
This is a nationwide collection without city sampling; historical validity and
complete coverage are not certified. No video is generated by collection.

```powershell
uv run python projects/india_railway_2026/collect_schedules.py --date 2026-10-15
```

## Scheduled-data test video

Generate a 60-second, 1080 × 1920, 30 fps timetable preview from the retained
snapshots, entirely offline and without an API key:

```powershell
uv run python projects/india_railway_2026/schedule_render.py
# Prepare data, poster and contact sheet without encoding:
uv run python projects/india_railway_2026/schedule_render.py --stills-only
# Audit an existing export without rendering again:
uv run python projects/india_railway_2026/schedule_render.py --verify-only
# Higher-quality final upload, with all 1,800 encoded frames audited:
uv run python projects/india_railway_2026/schedule_render.py --final
```

Open `media/india_railway_2026/scheduled_test/2026-10-15/SCHEDULED_TEST.mp4`.
The final command writes `media/india_railway_2026/final/2026-10-15/India_Railways_2026-10-15.mp4`
using H.264 CRF 18 instead of test CRF 23, with the same approved canvas and timing.
It reuses the scheduled movement cache and publishes only after every encoded frame
passes comparison. Source-data qualifications remain visible in the final video.
Both export directories hold a poster, contact sheet, mapping coverage and video
verification. The compressed prepared dataset stays in the test directory and is
shared by both commands. Test verification samples frames; final verification
compares every frame. Inputs are hash-checked before
reusing the prepared dataset; source snapshots are never modified. Only the main
dated projection is used; review-only schedules remain excluded.

Train identities and stop times come from the collected timetables. Movement
between stops is interpolated along inferred shortest OSM track paths, not a
verified itinerary or recorded position. Stations snap within 2.5 km; disconnected
tracks, excessive detours and speeds over 350 km/h are omitted. No missing track
connections or timings are invented. The preview reports how many journeys have
usable mapped travel, and counters/chart reflect displayed intervals only.
Incomplete journeys may contain gaps. Scheduled previews use eight service
groups, with their palette stored in the prepared dataset:

| Group | Colour | Classification |
| --- | --- | --- |
| Mail / Express | Blue `#0072B2` | Explicit Mail/Express type, or express evidence in the name |
| Superfast | Magenta `#A83D83` | Explicit Superfast/SF type, or SF/Superfast in the name when the source type is not definitive |
| Passenger / Regional | Deep violet `#6842A6` | Passenger, MEMU, DEMU and DMU; also Namo Bharat Rapid Rail/Vande Bharat Metro |
| Suburban / Local | Teal `#008B8B` | Suburban, local, EMU and MMTS |
| Vande Bharat | Orange `#E87818` | Vande Bharat family, including Sleeper; excludes the Metro/Rapid Rail variant |
| Rajdhani | Red `#BF3043` | Rajdhani family |
| Shatabdi / Jan Shatabdi | Oxford-blue-inspired `#27466B` | Both named families |
| Unknown service type | Grey `#6B7280` | Insufficient information; never silently treated as Express |

The palette is **livery-inspired**, not a reconstruction of each train's actual
paint scheme. Vande Bharat orange reflects the orange/grey variant shown in
[government imagery](https://static.pib.gov.in/WriteReadData/specificdocs/documents/2026/apr/doc2026415847301.pdf).
Rajdhani red, Shatabdi blue and conventional Mail/Express blue draw on the
[RDSO ICF coach painting manual](https://rdso.indianrailways.gov.in/uploads/files/Painting%2012.pdf).
These are representative associations: Vande Bharat also has white/blue variants,
and [some Rajdhani services use Tejas rakes](https://www.pib.gov.in/PressReleasePage.aspx?PRID=1782298&lang=2&reg=48).
The screen hex values are display approximations, not official paint codes.
Magenta, violet and teal distinguish the remaining broad service groups; they
do not assert universal Superfast, regional or suburban liveries. No zone-wide
colour or dated rake assignment is inferred. Prepared datasets and export audits
record `palette_basis`; the representative colour associations are documented here.

This is a display hierarchy: the three named families take priority over generic
speed classes. Other services use an explicit source service type before name
fallbacks. Intercity is not automatically treated as a stopping passenger service.
Duronto, Tejas, Garib Rath, Humsafar and Amrit Bharat use Mail/Express unless
Superfast is explicitly indicated; a brand alone does not establish that class.
Special/holiday operation is independent of service type: an SF Special remains
Superfast, an Express Special remains Express, and Special alone stays Unknown.
Neither animation speed nor a train-number pattern determines the category.
Raw source classifications remain unchanged and may themselves be imperfect.
The scheduled legend fits four rows in the existing canvas, with smaller marker
halos to reduce overlap.
City names stay fixed and are composited above train markers and trails, with a
thin background-coloured outline and no opaque label boxes. Native text and path effects keep the label glyphs above the moving collections.

The compact portrait layout keeps the daily journey total at the top, alongside
the title, date and clock. The map is enlarged uniformly by about 5.9%, preserving
the full boundary and island groups; the same display transform applies to tracks,
train positions and city anchors without modifying stored routes or distances.
The eight-group legend has no enclosing card. The activity graph labels the
current count as a fixed heading above the graph. The y-axis provides the activity
scale without a separate peak annotation. Counts come from exact movement-interval
boundaries, including station dwell, rather than the legacy five-minute activity
samples. For this dataset,
the exact peak is 2,402 at 08:02 IST; the older sampled maximum was 2,399.
The graph uses a rounded axis ceiling above the exact peak. Intro and
outro timing, the 1080 × 1920 canvas and 30 fps remain unchanged.
Data qualifications and attribution are consolidated in the footer; detailed
methodology and the livery-inspired palette basis remain documented here.
The video explicitly labels scheduled times, inferred paths and provisional
coverage. It does not show actual delays or certify national timetable completeness.

## Implementation

This is one offline scheduled-video workflow, not an application. Matplotlib's
headless Agg canvas draws the boundary, network, batched train markers/trails,
labels and activity axes. A cached background holds the static artwork; existing
artists update each frame and city labels are drawn last. PyAV streams frames
directly to H.264 through FFmpeg, without a Manim scene or intermediate movies.
Manim remains available in the shared environment for other projects.

`model.py` owns interpolation, half-open counts and continuous fade/trail rules.
`settings.py` keeps the palette, map layout and font-independent styling together.
`design.py` composes frames; `replay.py` exports and audits them.
`schedule_render.py` maps timetable legs with SciPy and coordinates the export.
There are no RailRadar, quota, manifest, synthetic-demo or socket-patching paths.

The prepared dataset is keyed by timetable/station/track input hashes, the official
boundary hash and `PREPARATION_VERSION` in `schedule_render.py`. Increment that
version when changing routing or movement preparation. Palette and layout edits
reuse the mapped movements; classifications refresh from retained source types.
A matching cache is read without rewriting its compressed geometry. A new render
is staged and audited before replacing the previous video and stills.
Publishing copies files into the output folder before atomic replacement so they
inherit normal Windows permissions rather than temporary-directory permissions.

The output remains **1080 × 1920, 30 fps, 1,800 frames, 60 seconds**, silent H.264
with yuv420p pixels: 3 seconds of introduction, 54 seconds covering the day, and a
3-second final hold. Markers fade within 0.15 video seconds at continuous interval
boundaries; trails retain seven simulated minutes through dwell and stop at gaps.

FFprobe checks format, duration, dimensions and frame count. PyAV decodes selected
encoded frames for comparison with the model, including clock endpoints, marker
patches and the final hold. `verification.json` states how many frames were checked;
a successful sampled audit does not claim that every frame was compared.
Pixel checks cannot certify upstream data or replace visual review.

## Tests and network maintenance

```powershell
uv run python -m unittest discover -s projects/india_railway_2026 -p 'test_*.py' -v
# Download missing pinned timetable snapshots only when explicitly requested:
uv run python projects/india_railway_2026/collect_schedules.py --date 2026-10-15 --download
# Explicit network-source refresh (not required to render retained assets):
uv run python projects/india_railway_2026/fetch_tracks.py
uv run python projects/india_railway_2026/prepare_tracks.py media/india_railway_2026/tooling/railways.geojson
```

Track refresh retains the source GeoJSON and ODbL attribution and freezes the full
network. The existing frozen geometry also contains historical demo routes, which
are unused. Timetable routing uses only its national network. Source snapshots,
licence notices and provenance remain in `assets/`; generated files stay in `media/`.
